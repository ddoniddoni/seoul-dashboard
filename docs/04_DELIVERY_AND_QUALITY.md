# 04. 운영, 배포와 품질 기준

기준: v1.0.0 / 2026-10-14  
이 문서는 운영 계획이며 예약 수집이나 실제 배포를 이미 실행했다는 뜻이 아니다. 공식 출처 주소는 03 문서의 S01~S18을 따른다.

## 1. 운영 형태

개인 비상업 포트폴리오를 기본 전제로 Vercel에 웹과 Node.js 함수를, Supabase에 DB와 예약 스케줄을 둔다. 상업 서비스로 전환하면 Vercel Hobby 사용 조건을 재검토한다. 근거: S18.

2026-11-10 기준 운영 DB 수집기는 20곳/5분 준비 상태이며 원격 마이그레이션은 미적용이다. 개발용 정기 수집도 모니터링 20곳/기본 5분 또는 선택 10분/30분을 적용한다. 실행 상태는 collector:local status와 PROGRESS.md의 최신 기록으로 확인한다. 지도 배경 타일, 로그인, 장기 원본 XML 보관과 Supabase Realtime은 필수 비용 항목으로 추가하지 않는다.

## 2. 요청량과 무료 범위

아래는 24시간 수집, 장소당 슬롯별 원천 호출 1회를 가정한 산술 추정이다. 실패 재시도, 수동 검증과 다른 키 사용처의 호출은 별도다.

| 활성 장소 | 수집 간격 | 기본 원천 요청/일 | 24시간 관측 row 상한 |
| --- | --- | --- | --- |
| 5 | 10분 | 720 | 720 |
| 5 | 5분 | 1,440 | 1,440 |
| 10 | 10분 | 1,440 | 1,440 |
| 20 (현재 기본) | 5분 | 5,760 | 5,760 |
| 20 | 10분 | 2,880 | 2,880 |
| 20 | 30분 | 960 | 960 |
| 121 | 10분 | 17,424 | 17,424 |
| 121 | 30분 | 5,808 | 5,808 |
| 121 | 3분 (이전 검토안) | 58,080 | 58,080 |

일일 기본 요청은 `장소 수 × 24 × 60 / 수집 간격(분)`으로 계산한다. 같은 원천 시각의 중복 수신은 이력 row를 늘리지 않지만 API 요청 횟수는 소비한다.

기본 DB 수집 앱 예산 6,000회는 서울시 공식 제한값이 아니라 안전장치다. 20곳/5분의 기본 요청은 5,760회로, 상한 내 재시도 여유는 240회다. 재시도가 많아 예산을 소진하면 다음 한국 날짜까지 중지한다. 로컬은 재시도 없이 5분 5,760회, 10분 2,880회, 30분 960회로 제한한다. 2026-10-15 확인한 서울시 공식 일반 인증키 안내에는 호출 횟수 제한이 없으며, 일일 1,000회는 실시간 지하철 전용 키의 정책이다. 근거와 개별 계정/초당 제한 미확인 범위는 [호출 정책 기록](sources/seoul-api-limits-20261015.json)을 따른다. 2026-11-10 사용자 요청에 따라 기본 대상을 20곳으로 준비했지만 수집기 활성화는 별도다. 정기 수집을 확장할 때 내부 예산, 동시성, 저장 용량과 전송 승인 범위를 함께 정한다.

서버 내부 일일 예산은 한국 시간 자정 기준으로 잡되, 원천의 제한 구간이 다르면 그 구간의 한도를 별도로 준수하도록 수정한다. 다른 앱에서도 같은 키를 쓴다면 이 수집기의 DB 카운터만으로 전체 사용량을 알 수 없다.

Supabase 공개 요금표에는 Free DB 500 MB, egress 5 GB와 비활성 프로젝트 중지 조건이 있다. 이 제한과 실제 사용량을 배포 직전에 다시 확인한다. 정기 작업이 있다는 이유만으로 영구 활성화나 무중단 운영을 보장하지 않는다. 근거: S08.

브라우저 20개가 각각 60초마다 자체 조회 API를 읽으면 시간당 1,200회 조회다. 이 요청은 서울시 호출과 별개다. 짧은 공유 캐시로 DB 부하를 줄이되, 캐시 hit 비율과 호스팅 전송량은 실측한다.

## 3. 환경변수 계약

| 변수 | 요구 시점 | 주의 |
| --- | --- | --- |
| `DATA_MODE` | 기본 live | 이전 demo 값도 live로 해석. 공개 화면은 실데이터 전용 |
| `LIVE_DATA_BACKEND` | live 읽기, 기본 supabase | local-snapshot은 개발 수집본/기본 5분, 선택 10분 또는 30분 정기 수집용, production 거부 |
| `APP_BASE_URL` | 배포와 링크 생성 | 운영에서는 고정 HTTPS origin |
| `SEOUL_API_KEY` | API 검증/수집 | 서버 전용 비밀 |
| `SEOUL_API_BASE_URL` | API 검증/수집 | 허용된 원천 host와 port만 |
| `SEOUL_ALLOW_INSECURE_HTTP` | HTTP 원천 사용 시 | false가 기본, 명시 승인 필요 |
| `SEOUL_SOURCE_TIME_ZONE` | M2 API 검증/수집 | 기본 공란. 현재 허용 해석은 Asia/Seoul. 공식 근거는 미확인 |
| `SUPABASE_URL` 또는 `NEXT_PUBLIC_SUPABASE_URL` | live 읽기/수집 | HTTPS *.supabase.co 또는 로컬 HTTP 127.0.0.1/localhost:54321 |
| `SUPABASE_PUBLISHABLE_KEY` 또는 `NEXT_PUBLIC_SUPABASE_ANON_KEY` | live 읽기 | sb_publishable_ 형식, 공개 읽기 RLS 적용 |
| `SUPABASE_SECRET_KEY` 또는 `SUPABASE_SERVICE_ROLE_KEY` | 수집 | sb_secret_ 또는 대상 프로젝트의 유효한 service_role JWT. 서버 전용 |
| `COLLECTOR_ENABLED` | 기존 DB 수집 | false가 기본. 개발 collector:local 실행은 독립 명령 |
| `COLLECTOR_SECRET` | 수집 endpoint | 영문/숫자/밑줄/하이픈 32~256자 무작위 값, Vault와 배포 설정에 저장 |
| `COLLECTION_INTERVAL_MINUTES` | 수집 | 5만 허용, DB 슬롯과 Cron 표현식도 5분으로 일치 |
| `MAX_MONITORED_AREAS` | 수집 | 1~20, 기본 20. 초과 설정은 시작 전 거부 |
| `SEOUL_DAILY_CALL_BUDGET` | 수집 | 1~6000, 기본 6000. 실제 원천 제한 이하로 설정 |

환경변수 검증은 기능별로 분리한다. 내부 합성 계약 테스트에는 실데이터 비밀을 요구하지 않는다. 공개 live 읽기는 Supabase 읽기 설정만 필요하다. 로컬 원천 API 테스트는 서울시 설정만 필요하다. 수집기 활성화에는 모든 수집 설정과 DB 권한이 필요하다.

문자열 `false`를 `Boolean(value)`로 변환하지 않는다. bool은 `true`/`false`를 명시 비교하고 숫자는 정수, 최솟값과 최댓값을 검증한다.

로컬 실제 값은 `.env.local`에 저장한다. 구현 시 `.gitignore`에 `.env*`를 제외하되 `!.env.example`만 허용하고 기존 정책과 병합한다. 예시 파일에 실제 키가 복사되지 않았는지 검사한다.

## 4. HTTP 원천 전송 게이트

공식 예시의 HTTP origin을 임의로 HTTPS로 바꿨다고 보안 문제가 해결되는 것은 아니다. 지원하지 않는 TLS 포트로 요청하거나 인증서 검증을 끄지 않는다.

M0에서 최신 공식 HTTPS endpoint가 있는지 확인하고, 실제 서버 환경에서 인증서와 응답을 검사한다. 확인되면 해당 HTTPS origin을 설정한다. 확인되지 않은 주소로 키를 보내지 않는다.

HTTP만 제공되는 경우에는 원천 구간의 키가 평문으로 전송된다는 위험을 `PROGRESS.md`에 남긴다. 사용자 데이터, Supabase 키와 수집 토큰을 그 구간에 보내지 않는다. 공개 운영은 위험을 이해한 운영자의 명시 승인 후 `SEOUL_ALLOW_INSECURE_HTTP=true`로 진행한다.

M2 allowlist에는 실제로 확인한 `http://openapi.seoul.go.kr:8088`만 등록했다. HTTPS는 검증 전까지 키 전송 대상에 추가하지 않는다. `verify:seoul`은 기본 설정 확인이고 `--execute`가 있어야 호출한다. 로컬의 별도 HTTP 1회 승인을 받은 경우 `--allow-insecure-http-once`를 사용할 수 있으며, `.env.local`의 false를 바꾸거나 운영 승인을 남기지 않는다. 앞선 1회 승인을 새로운 실행에 재사용하지 않는다. `capture:seoul --execute --allow-insecure-http-once`는 기본 20곳, `--all` 추가 시 전체 공식 121곳 단일 배치다. 각 배치는 정확한 요청 횟수와 평문 키 전송에 대한 명시 승인을 받은 뒤 실행하며 전역 HTTP/예약 수집 설정을 바꾸지 않는다. 2026-10-15 전체 배치는 자동 승인 검토가 범위별 명시 승인 부족으로 차단한 뒤, 사용자가 이번 121곳 각 1회 단일 평문 HTTP 조회를 명시 승인하여 실행했다. 요청 121회로 해당 승인을 모두 사용했으며 이후 배치/운영/정기 수집에 재사용하지 않는다.

2026-10-16 개발용 정기 명령은 `collector:local start --interval-minutes=10 --execute --source-time-zone=Asia/Seoul --allow-insecure-http-recurring`이다. 처음 3분/121곳으로 준비한 뒤 사용자의 포트폴리오 주기 검토에 맞춰 기본 10분/선택 30분으로 변경했다. 30분을 선택하면 --interval-minutes=30을 사용한다. 실제 시작 전에는 선택한 주기의 인증키 반복 평문 HTTP 전송 범위(배치당 최대 20회, 기본 5분 주기 일일 예산 5,760회, 선택 10분 2,880회 또는 30분 960회, 중지할 때까지)에 대한 승인을 확인한다. 기존 단일 실행 승인을 재사용하거나 전역 HTTP 설정을 변경하지 않는다. 시작/상태/중지/일시 중지 해제 명령과 작업 기한/일일 원장/이력 상한은 README의 개발용 정기 수집 계약을 따른다. 실제 실행 여부와 전송 승인/차단 결과는 PROGRESS.md에 남긴다.

`SEOUL_SOURCE_TIME_ZONE` 또는 CLI 시간대 옵션은 실행자가 선택한 문자열 해석 기준이다. 원천 응답/공식 문서가 시간대를 확정한 증거로 보고하지 않는다. 공식 근거가 확인되면 이 설정 게이트와 문서를 함께 갱신한다.

이 동의를 얻기 위해 키 자체를 대화에 붙여 넣도록 요구하지 않는다. HTTP 사용 여부만 결정한다. 키를 숨기는 서버 프록시와 전송 암호화는 별개의 문제다.

## 5. 예약 수집 설정

Supabase Cron과 pg_net을 활성화한 뒤 고정 운영 origin과 수집 토큰을 Vault에 각각 `seoul_pulse_origin`, `seoul_pulse_collector_secret` 이름으로 저장한다. 실제 값을 migration이나 Git 파일에 기록하지 않는다.

원격 수집용 [예약 활성화](../supabase/templates/cron-enable.sql), [예약 해제](../supabase/templates/cron-disable.sql)는 미실행이며 [운영 순서](../supabase/README.md)를 따른다. 활성화 템플릿은 Vault 형식/활성 장소/동명 수집 job을 확인해 중복 등록을 거부한다. 2026-11-12 [DB 정리 활성화](../supabase/templates/cleanup-cron-enable.sql)는 별도로 실행했다. 매시 23분에 관측 48시간, 완료 실행/예산/우리 앱 Cron 종료 로그 14일 보존을 적용한다. 최신값, 열린 circuit과 활성 lease는 보존한다. 정상 정리 간격 사이의 삭제 대기분은 위 24시간 관측 수와 별도다.

다음은 **검증 후 운영자가 실행할 템플릿**이다. 이 문서 작성 시 실행하지 않았다. Vault 값의 존재, HTTPS origin과 인증 검증을 먼저 확인한다.

```sql
select cron.schedule(
  'seoul-pulse-collect-v1',
  '*/5 * * * *',
  $$
  select net.http_post(
    url := (
      select decrypted_secret
      from vault.decrypted_secrets
      where name = 'seoul_pulse_origin'
    ) || '/api/internal/collect',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'Authorization', 'Bearer ' || (
        select decrypted_secret
        from vault.decrypted_secrets
        where name = 'seoul_pulse_collector_secret'
      )
    ),
    body := '{}'::jsonb,
    timeout_milliseconds := 55000
  );
  $$
);
```

HTTP 예약의 기본 timeout에 의존하지 않는다. 앱은 최대 45초 작업 후 종료 기록을 마무리하고 DB 기한은 50초다. 예약 HTTP 대기는 55초, route 설정은 60초로 둔다. 실제 pg_net/호스팅 지원 범위와 네트워크 지연은 활성화 전에 검증한다. HTTP 대기가 끝나도 서버 작업이 중단됐다고 단정하지 않고 실행 원장을 확인한다. 근거: S06, S09.

Cron SQL이 성공했다는 사실만으로 수집 성공을 판단하지 않는다. pg_net HTTP 응답과 앱의 `sp_collection_runs`, 실제 관측 row의 갱신을 함께 확인한다. 비동기 HTTP 큐에 요청이 등록된 상태와 데이터 저장 완료 상태는 다르다.

동일 job 이름을 다시 등록할 때 기존 작업이 변경될 수 있으므로 중복 여부를 확인한다. 웹 Preview 배포마다 Cron을 만들지 않는다. 운영용 스케줄은 하나만 유지한다. 근거: S06.

수집 비활성화는 앱의 `COLLECTOR_ENABLED=false`와 해당 Cron 비활성화로 수행한다. 테이블과 수집한 기록을 지우는 조치와 구분한다.

## 6. 공개 배포 체크리스트

`npm run check:deployment`는 외부 호출 없이 운영 설정을 검사하고, `-- --read`는 공개 DB 읽기를 확인한다. `-- --collector`를 추가하면 수집 설정도 검사한다. 자세한 적용 순서와 읽기 전용 SQL은 [운영 DB 안내](../supabase/README.md)를 따른다. 실제 적용/검증 상태는 PROGRESS.md에 기록한다.

### 애플리케이션

실제 데이터 읽기 설정, 앱 origin, 수집 활성화 여부를 Preview와 Production별로 구분한다. Preview도 실데이터 전용이며 읽기 전용 DB 연결만 설정한다. 운영 수집 토큰과 관리자 비밀을 주입하지 않는다.

production build가 서울시 API에 직접 접근해야만 성공하는 구조를 만들지 않는다. 빌드와 외부 수집을 분리하고, 실제 데이터는 요청 시 읽는다.

내부 수집 endpoint는 POST와 인증 검사를 모두 적용하고 `no-store`로 응답한다. 보호된 배포 주소가 Cron 요청을 막는다면 전체 배포 보호를 무작정 해제하지 않고 해당 호출의 접근 정책을 검토한다.

### 데이터와 권한

정식 장소 코드와 지도 자료가 연결되어야 한다. RLS, 공개 SELECT 허용 범위, 비공개 RPC 실행 권한을 자동 테스트한다. secret key가 RLS를 우회한다는 점을 고려하고 읽기 경로와 관리 경로를 분리한다. 근거: S15, S16.

원천 사용량 확인, 앱 예산, 요청당 timeout, 중복 슬롯/lease 검사, 재시도 제한과 보존 작업을 모두 설정한다. 수집된 과거 기록이 없는 상태의 화면도 직접 확인한다.

### 공개 표현

실제/데모 표기, 데이터 출처, 재가공 설명, 추정 범위와 기준 시각을 확인한다. 호스팅이나 지도 서비스의 무료 조건을 영구 보장처럼 안내하지 않는다.

지도에 외부 타일을 추가하면 출처 표시, 허용 트래픽, 캐시와 다운로드 정책을 확인한다. 공용 OSM 타일을 대량 사전 다운로드하거나 영구 무료 CDN처럼 사용하지 않는다. 근거: S11.

## 7. 보안과 악용 방지

인증 토큰은 길이를 검증한 후 안전하게 비교한다. 인증 실패 시 DB 잠금 획득이나 서울시 호출을 수행하지 않는다. 공개 status에 운영 비밀, 원천 요청 URL, 내부 오류 stack과 private 테이블을 노출하지 않는다.

API 호출 URL은 서버 allowlist와 등록 장소 코드로만 구성한다. 사용자가 `url=`, `host=`, 임의 서비스명이나 경로를 주입하는 요청은 거부한다. redirect를 무조건 따라가며 키를 다른 host로 전송하지 않는다.

수집 결과의 메시지는 일반 텍스트로 렌더링한다. 날짜/정렬/장소 입력을 검증하고, SQL은 안전한 바인딩 또는 검증된 RPC 인자를 사용한다. XML 바이트/깊이 제한과 CSV 수식 실행 방지를 포함한다.

로그에는 areaCode, requestId, 상태 코드, 응답 크기와 소요시간 정도만 기록한다. 원천 URL의 키가 경로에 있으므로 query string 제거만으로는 충분하지 않다. 오류 객체와 APM의 자동 HTTP 기록에서도 전체 원천 URL을 지우거나 마스킹한다.

## 8. 테스트 기준

| 영역 | 필수 사례 |
| --- | --- |
| XML 계약 | 정상, 반복 1개/여러 개, 블록 없음, 다른 envelope, HTTP 200 오류 |
| 파서 방어 | DOCTYPE/ENTITY, HTML 페이지, 크기 초과, 잘못된 XML |
| 숫자 | 빈 값, `0`, 쉼표, 음수 인구, 음수 기온, 하한>상한 |
| 시각 | KST 변환, 자정 경계, 미래 시각, 원천 시각 없는 값 |
| freshness | 30/60분 경계, 같은 원천값 재수신, 수집 실패와 독립 |
| 최신 저장 | 중복, 같은 시각 수정, 과거 응답, 인구 성공/날씨 실패 |
| DB 원자성 | 최신값과 이력의 부분 commit 방지, CHECK 제약 |
| 수집 | 중복 슬롯, 동시 실행, lease 만료, 기한 종료와 부분 성공 |
| 예산 | 모든 시도/재시도 계수, 마지막 1회 경쟁, 예산 소진 |
| 권한 | anon SELECT 범위, 쓰기 거부, private 접근과 관리 RPC 실행 거부 |
| URL | 새로고침/뒤로가기, 잘못된 코드, 최대 3개, 데이터셋 유지 |
| 데이터 모드 | demo와 live 캐시 분리, 실패 시 자동 교체 없음 |
| 지도 | 지도 실패 시 목록 사용, 재조회 후 카메라/선택 유지 |
| 차트 | 결측 연결 금지, 기간 부족 안내, 동일 범위 비교 |
| CSV | 출처와 mode, 한글, 인용부호, 개행, 수식 문자열 |
| 접근성 | 키보드, 포커스, 대체 목록, 색상 외 의미, 대비 |
| 배포 | 비밀 번들 노출 없음, 오류 응답 no-store, 외부 연결 없는 demo build |

E2E 기본 시나리오는 demo로 재현한다. 실제 원천 API를 CI의 매 테스트마다 호출하지 않는다. 계약 테스트는 비밀을 제거한 fixture와 합성 오류 fixture를 사용한다. 실제 API smoke test는 별도 명시 실행으로 분리한다.

DB 통합 테스트는 승인된 테스트 DB 또는 로컬 Supabase에서 실행한다. 운영 DB에 테스트 데이터를 쓰거나 정리 명목으로 production reset을 하지 않는다.

## 9. 검증 명령과 수행 시점

아래는 개발 과정에서 제공할 npm scripts의 목표 목록이다. M0에서 dev/lint/typecheck/test/build의 최소 기반을 만들고, E2E는 M1 이후, verify:seoul은 M0/M2, DB 통합 검사와 collect:once는 M3에서 실제 구현에 맞춰 연결한다. 이름만 만들고 성공을 반환하는 가짜 script를 넣지 않는다. 아직 구현하지 않은 명령을 실행 가능하다고 보고하지 않는다.

```text
npm run dev
npm run lint
npm run typecheck
npm run test
npm run test:integration
npm run test:e2e
npm run build
npm run verify:seoul
npm run collect:once
```

`verify:seoul`은 로컬 비밀 설정을 로드하되 값을 출력하지 않는다. `collect:once`는 보호된 수집기와 같은 코어 함수를 사용하고 테스트 대상/원격 쓰기 여부를 명확하게 확인한다.

작은 변경은 관련 테스트와 필요한 타입 검사로 빠르게 확인한다. 단계 종료에는 lint, typecheck와 해당 단계 테스트를 수행한다. DB 작업이 있으면 integration 테스트를 추가한다. 배포 후보에는 build와 E2E까지 모두 실행한다.

매 수정마다 전체 build, CI 대기와 추가 분석기를 반복하지 않는다. 반대로 최종 검증을 생략하고 화면이 보인다는 이유만으로 완료 처리하지 않는다.

## 10. 성능 측정

목표는 설계값이며 아직 달성한 실적이 아니다. 1440px 데스크톱과 390px 모바일 조건에서 동일한 demo fixture로 비교한다.

첫 화면에서 필요한 요약 JSON은 100 KB 이하를 목표로 한다. 차트 데이터는 최근 24시간 144개 버킷을 기본으로 하며 경계 처리에 따라 추가되는 부분 버킷은 응답에 설명한다. 지도/차트 chunk와 원천 XML은 초기 HTML 데이터에 포함하지 않는다.

실험실 측정의 LCP 2.5초 이하, CLS 0.1 이하를 초기 목표로 한다. 측정 도구, 기기/네트워크 조건, 반복 횟수와 결과를 남긴다. 실제 사용자 INP와 실험실의 대체 지표를 혼동하지 않는다.

실제 프로파일로 지도 재생성, 데이터 갱신 때 전체 재렌더링, 중복 fetch와 불필요한 JSON 크기를 확인한다. 개선 전후의 같은 조건 측정이 있을 때만 포트폴리오에 성능 개선 수치를 쓴다.

## 11. 장애 대응 절차

| 증상 | 확인 | 처리 |
| --- | --- | --- |
| 모든 장소가 지연 | Cron, HTTP 응답, 앱 실행 기록, DB 연결 | 스케줄/연결 복구, 과거 정상값 유지 |
| 인증 오류 | 서버 설정, 키 변경, 권한 | 후속 원천 호출 중지, 값 노출 없이 교체 |
| 요청 제한 | 원천 코드, 일일 예산, 중복 작업 | circuit 적용, 주기/장소 수 검토 |
| 특정 장소만 실패 | 공식 코드, section과 XML 계약 | 해당 장소만 격리, 다른 장소 계속 처리 |
| DB 저장 실패 | 권한, 용량, transaction 오류 | 수집 기록 확인, 복구 전 가짜 최신 시각 금지 |
| 지도 실패 | asset 경로, 좌표계, WebGL | 목록 유지, 지도 오류 안내 |
| 무료 프로젝트 중지 | 제공사 Dashboard와 상태 | 재개 후 갭 유지, 필요하면 운영 방식 변경 |

운영 점검에는 최근 수집 성공 시각, 활성 장소 수, 성공/실패/중단 수, 원천 요청 시도 수, 원천 시각의 나이와 DB 크기를 사용한다. 주기적 신호가 없을 때의 알림은 향후 별도 운영 도구로 추가할 수 있지만, 현재 설정하지 않은 알림을 활성 상태로 표시하지 않는다.

복구 후에도 누락 구간은 채워졌다고 가정하지 않는다. 과거를 다시 받을 수 없는 원천이라면 해당 구간은 결측으로 남긴다.
