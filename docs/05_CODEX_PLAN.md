# 05. Codex 단계별 개발 계획

기준: v1.0.0 / 2026-10-14  
진행 상태의 기준 파일: `../PROGRESS.md`

## 1. 작업 원칙과 문서 사용법

현재 단계 하나만 수행한다. 작업 시작 시 기존 파일과 사용자 변경을 확인하고, 필요한 문서의 관련 부분부터 읽는다. 앱 전체를 한 번에 생성한 뒤 외부 데이터 계약을 끼워 맞추지 않는다.

| 판단 대상 | 기준 문서 |
| --- | --- |
| 기능, 화면, 표시 문구와 상호작용 | `01_PRODUCT_AND_UI.md` |
| 코드 경계, 조회 상태, 캐시와 기술 선택 | `02_ARCHITECTURE.md` |
| 정규화 타입, API, DB, 수집과 데이터 해석 | `03_DATA_AND_API.md` |
| 환경변수, 보안, 운영과 검증 | `04_DELIVERY_AND_QUALITY.md` |
| 현재 작업 순서와 통과 조건 | 이 문서 |
| 실제 수행 내용과 외부 연결 상태 | `../PROGRESS.md` |

문서와 실제 API가 충돌하면 공식 명세와 비밀을 제거한 실제 응답을 확인하고, 내부 계약에 미치는 영향을 기록한 뒤 문서를 수정한다. 원천 필드가 없는데 코드만 통과시키려고 가짜 기본값을 넣지 않는다.

단계 상태는 `미시작`, `진행 중`, `구현 완료 / 외부 검증 대기`, `검증 완료`, `차단`으로 구분한다. 구현 완료가 운영 활성화나 배포 완료를 뜻하지 않는다.

## 2. 전체 흐름

```text
M0 기반과 외부 계약 확인
  → M1 데모 데이터 기반 UI
  → M2 실제 API adapter
  → M3 DB와 수집 파이프라인
  → M4 지도, 시계열과 비교 완성
  → M5 장애, 접근성과 성능 검증
  → M6 배포 준비와 승인된 공개 전환
```

API 연결이나 외부 계정 설정이 막혀도 M1은 진행할 수 있다. 단, M0의 미확인 항목은 지우지 않는다. M4 UI도 명시적 demo 데이터로 먼저 개발할 수 있지만, 실제 지도 자산과 수집 이력의 통합 검증은 별도로 남긴다.

M3 이후 승인된 개발용 수집을 일찍 시작하면 실제 이력을 확보할 수 있다. 그렇더라도 승인 없이 원격 DB를 수정하거나 예약 수집을 켜지 않는다. 수집 시작 전 과거 기록은 생성할 수 없으므로 UI에서 빈 기간을 설명한다.

## 3. M0. 기반과 외부 계약 확인

### 목표

문서를 안전하게 프로젝트에 통합하고, 구현을 시작할 수 있는 최소 실행 환경과 외부 의존성 확인표를 만든다.

### 작업

1. 기존 코드, 문서, npm 설정과 사용자 변경을 확인한다. 저장소 초기화나 기존 파일의 무조건 덮어쓰기는 금지한다.
2. 호환되는 안정 Next.js, React, TypeScript와 Node.js LTS를 확인한다. 실제 설치 버전과 선택 이유를 진행 문서에 기록하고 npm lockfile을 관리한다.
3. 최소 App Router 화면, TypeScript strict, 환경변수 경계, 기본 스타일과 테스트 기반을 구성한다. 현재 단계에 필요 없는 빈 디렉터리와 서비스는 만들지 않는다.
4. 공식 카탈로그에서 초기 5개 후보 생활권에 대응하는 장소 이름과 코드를 확인한다. 비슷한 이름의 장소가 여러 개면 선택 근거를 기록한다.
5. 공식 장소 영역 자료의 형식, 좌표계, 이용 조건과 버전을 확인한다. 확인하지 못한 좌표나 폴리곤을 임의로 넣지 않는다.
6. HTTPS 제공 여부와 실제 호스팅에서의 원천 연결 가능성을 확인한다. HTTP만 확인되는 경우 운영 문서의 명시적 승인 절차를 남기고 기본 거부 설정을 유지한다.
7. 로컬에 키가 있고 전송 조건이 허용된 경우, 한 장소를 최소 횟수로 호출한다. 응답 envelope, 결과 코드, 원천 기준 시각, 혼잡 단계와 선택 필드를 검증한다. 키가 포함된 URL과 비밀값은 출력하지 않는다.
8. 발급 계정의 호출 허용량과 이용 조건을 확인한다. 문서의 일일 1,000회는 프로젝트 예산이지 발급 키의 보장 한도가 아니다.

### 산출물

실행 가능한 최소 화면, 현재 단계 검증 scripts, 비밀값 없는 환경변수 예시, 확인된 장소 카탈로그 또는 미확인 목록, API 계약 확인 결과, 갱신된 `PROGRESS.md`다. 비밀을 제거한 응답 fixture를 보관할 경우 크기를 줄이고 원천 정보를 기록한다.

### 통과 조건

개발 서버와 최소 테스트가 동작하고, 실제 버전과 외부 의존성 상태를 설명할 수 있어야 한다. 실호출을 못 했으면 `구현 완료 / 외부 검증 대기`로 기록한다. 존재하지 않는 API 응답, 장소 코드나 검사 결과를 채우지 않는다.

실행 가능한 scripts에 한해 lint, typecheck와 기본 테스트를 수행한다. 초기 빌드 가능 여부는 한 번 확인한다. 외부 연결 없는 demo 빌드를 목표로 하고, 키나 DB가 없다는 이유로 모든 페이지의 빌드가 실패하지 않게 한다.

## 4. M1. 데모 데이터 기반 UI

### 목표

원천 API와 DB 없이도 화면 품질과 사용자 흐름을 검토할 수 있는 첫 완성 형태를 만든다.

### 작업

공통 DTO와 `DemoRepository`를 구현하고 고정된 합성 fixture를 준비한다. demo에서는 현재 시점에 맞춘 상대 시각을 사용해도 되지만 합성 데이터 표시를 유지한다. 테스트에서는 고정 clock과 seed를 주입해 재현성을 확보한다.

대시보드 레이아웃, KPI, 장소 목록, 상세 화면, 데이터 안내와 기본 시계열을 구현한다. 지도는 후속 자산 검증이 필요하면 준비 상태로 표시하되 대체 목록은 완전히 사용할 수 있어야 한다.

URL 파싱과 링크 생성 함수를 먼저 공유한다. `dataset`, 선택 장소와 필터가 이동, 새로고침과 뒤로가기에서 유지되게 한다. demo/live 전환 시 이전 캐시와 즐겨찾기가 섞이지 않게 한다.

로딩, 조회 오류, 빈 데이터, 부분 성공, 지연과 수집 기간 부족 상태를 같은 단계에서 구현한다. 컬러뿐 아니라 문구와 아이콘으로 상태를 구분한다.

### 산출물과 통과 조건

390px 모바일과 1440px 데스크톱에서 기본 탐색이 가능하고, 로그인 없이 `/demo`로 시연할 수 있어야 한다. DB나 API 키가 없어도 demo가 동작해야 한다.

개요 KPI의 기준 범위, 추정 인구의 상하한, 원천 시각과 수집 시각이 구분되어야 한다. 합성 값이 실제 서울 데이터처럼 보이면 통과하지 못한다. URL과 상태 표시 컴포넌트 테스트를 포함한다.

## 5. M2. 실제 API adapter

### 목표

원천 XML을 UI와 분리된 안정적인 도메인 모델로 변환한다.

### 작업

서버 전용 API client, host allowlist, timeout, 바이트 제한과 비밀값 제거를 구현한다. 검증된 정상 envelope와 오류 응답을 구분하고 DOCTYPE/ENTITY, HTML 응답과 잘못된 XML을 거부한다.

인구와 날씨 section을 별도로 검증한다. 결측을 `0`으로 바꾸지 않고 알 수 없는 혼잡 단계는 `unknown`으로 처리한다. 문자열 시각의 시간대를 확인해 명시적으로 변환한다.

실제 응답으로 확인된 필드만 연결한다. 날씨 필드 확인이 끝나지 않으면 해당 부분은 `not-provided` 또는 적절한 오류 상태로 두며, 인구 기능을 막지 않는다.

`verify:seoul`을 실제 동작하도록 완성한다. 이 명령은 원천 확인을 위한 명시 실행이며 DB 쓰기와 정기 수집 활성화를 포함하지 않는다.

### 산출물과 통과 조건

정상 fixture, 오류 fixture, 정규화 코드와 계약 테스트를 제공한다. HTTP 200 오류, 빈 숫자, 음수 기온, 잘못된 인구 범위, 단일/반복 블록과 누락 시각을 검증한다.

실호출이 허용되는 환경이면 한 장소의 실제 응답과 정규화 결과를 대조한다. 그렇지 않으면 외부 검증 대기로 남긴다. 브라우저에서 원천 키나 원천 요청 URL이 발견되면 통과하지 못한다.

## 6. M3. DB와 수집 파이프라인

### 목표

공개 조회와 원천 수집이 분리된 실제 데이터 흐름을 구현한다.

### 작업

공개 장소/최신값/인구 이력 테이블과 비공개 실행/lease/예산 테이블의 migration을 작성한다. RLS, CHECK, 인덱스와 관리 RPC 권한을 함께 작성한다. 원격 적용은 별도 승인이 있을 때만 수행한다.

publishable key 기반 읽기 Repository와 secret key 기반 수집 클라이언트를 분리한다. 공개 API를 호출하거나 페이지를 새로고침해도 원천 요청이 발생하지 않도록 의존성 경계를 테스트한다.

슬롯 중복 방지, lease 토큰, 원자적 예산 예약, 제한된 동시성, deadline과 부분 성공을 구현한다. 같은 원천 시각의 재수신/수정과 과거 응답을 처리하고 최신값과 이력을 원자적으로 저장한다.

내부 수집 endpoint, `collect:once`, 예약 생성/해제 템플릿과 정리 작업을 준비한다. `COLLECTOR_ENABLED=false`를 초기값으로 유지한다.

### 산출물과 통과 조건

migration, 권한 테스트, 수집 통합 테스트와 실제 조회 API를 제공한다. 테스트 대상은 승인된 테스트 DB 또는 로컬 Supabase여야 한다.

같은 슬롯 요청 두 개가 원천 호출량을 두 배로 만들지 않아야 한다. 중복 관측이 이력을 늘리지 않아야 하며, 익명 요청의 쓰기와 관리 RPC 접근은 거부되어야 한다. 남은 예산 1회에 두 worker가 경쟁해도 한 번만 예약되어야 한다.

원격 DB나 예약 작업을 활성화하지 않았다면 코드 준비 상태와 운영 미활성 상태를 구분한다. 사용자 승인 없이 DB를 생성/초기화하거나 Cron을 등록하지 않는다.

## 7. M4. 지도, 시계열과 비교 완성

### 목표

지도, 목록, 차트와 URL이 연결된 분석 경험을 완성한다.

### 작업

검증된 장소 GeoJSON을 가공하고 원본 출처, 좌표계 변환과 버전을 기록한다. MapLibre에 안정적인 Feature ID를 부여하고 장소 선택을 목록과 URL에 동기화한다. 외부 배경 타일 없이도 장소를 탐색할 수 있게 한다.

10분/1시간 버킷, 명시적 결측과 부분 버킷 표시를 구현한다. 모든 비교 장소에 동일한 기준 시각과 구간을 사용한다. 원천 추정 범위와 범위 중앙값을 구분해서 표시한다.

최대 3개 장소 비교, 즐겨찾기, 공유 가능한 URL과 CSV 내보내기를 구현한다. CSV의 dataset, 출처, 관측 시각과 수식 문자열 처리를 검증한다.

자료가 부족하면 실제 수집 기간을 보여준다. 24시간/7일 그래프를 채우기 위해 실데이터 화면에 합성 관측을 넣지 않는다. 검증된 날씨 항목만 보조 카드로 추가한다.

### 산출물과 통과 조건

지도 클릭과 목록 선택이 일치하고, 재조회 후 선택과 카메라 위치가 보존되어야 한다. 지도 로딩 실패 시 목록과 상세 탐색은 유지되어야 한다.

새로고침, 뒤로가기, 잘못된 장소 코드, 네 번째 비교 대상, live/demo 전환과 결측 시계열을 테스트한다. 공유 링크를 새 브라우저에서 열어도 같은 비교 조건을 복원할 수 있어야 한다.

## 8. M5. 장애, 접근성과 성능 검증

### 목표

정상 화면뿐 아니라 실제 배포에서 생기는 실패 상황을 견디게 한다.

### 작업

API 지연, 원천 제한, DB 장애, 오래된 원천값, 부분 수집 실패, 오프라인과 숨겨진 탭을 재현한다. 직전 정상 데이터 유지와 상태 안내를 확인한다. 원천 오류나 DB 오류의 민감한 내용은 사용자 응답에서 제거한다.

키보드 이동, 포커스 복원, 목록 기반 지도 대체, 상태 의미와 대비를 검증한다. `prefers-reduced-motion`과 좁은 화면에서의 표/차트 사용성도 확인한다.

지도 인스턴스 중복 생성, 이벤트 누수, 초기 중복 fetch, 불필요한 전체 리렌더링과 응답 크기를 측정한다. 동일 조건의 전후 측정이 있을 때만 성능 개선 수치를 기록한다.

### 산출물과 통과 조건

운영 문서의 필수 테스트 표에서 구현 범위에 해당하는 항목을 확인한다. 공개 endpoint의 관리자 키 사용, 내부 수집의 무인증 실행, 실데이터/데모 혼합과 과거 결측의 위조는 출시 차단 결함으로 취급한다.

핵심 E2E는 네트워크에 의존하지 않는 demo에서 재현 가능해야 한다. 실호출 테스트는 별도 절차로 남긴다. 테스트를 실행하지 못한 환경 제약을 결과에 명시한다.

## 9. M6. 배포 준비와 승인된 공개 전환

### 목표

배포 가능한 후보를 만들고 실제 운영을 켤 때의 조건과 되돌리는 방법을 확인한다.

### 작업

전체 lint, typecheck, 단위/통합 테스트, build와 E2E를 실행한다. 제외한 검사가 있으면 이유와 위험을 남긴다. 외부 비밀 없이 demo 빌드가 가능하고 live 설정 누락이 명확하게 표시되는지 확인한다.

호스팅 조건, 함수 실행 한도, 원천 전송 보안, 실제 키 허용량, Supabase 사용량과 DB 보존 정책을 재확인한다. 개인 비상업용 배포가 아닌 범위로 확장하면 호스팅 약관을 다시 검토한다.

비밀 설정, 고정 수집 URL, 인증 토큰, Vault 참조, Cron 시간표와 중복 job 유무를 점검한다. 원격 작업 승인 이후에만 Preview/Production 배포, migration 적용과 Cron 활성화를 수행한다. Preview가 Production DB에 테스트 쓰기를 하지 않도록 분리한다.

운영 활성화가 승인되면 한 번의 수집과 한 번의 예약 실행을 확인한다. source timestamp, 실제 호출 수, 이력 행과 화면 반영을 대조하고 수집 중지/예약 해제 절차도 확인한다.

### 산출물과 통과 조건

최종 README에는 실행 방법, 구현 화면, 아키텍처, 데이터 해석, 실데이터/데모 구분, 운영 한계와 측정된 결과를 담는다. 구현 화면은 실제 앱에서 캡처하고 만들어낸 성능 수치를 쓰지 않는다.

실제로 확인된 배포 URL과 운영 상태만 기록한다. 배포 승인이 없거나 외부 검증이 남아 있으면 `배포 후보 준비 / 운영 전환 대기`로 마무리한다. URL을 추측해 만들거나 예약 작업을 활성 상태로 보고하지 않는다.

## 11. 단계 시작용 지시문

`M번호`를 실제 진행 문서의 다음 단계로 바꿔 사용한다.

```text
AGENTS.md와 PROGRESS.md를 읽고 현재 저장소 상태를 확인해줘.
docs/05_CODEX_PLAN.md의 M번호 단계만 진행해줘.
관련 제품, 아키텍처, 데이터, 운영 문서의 요구사항을 함께 적용해줘.

기존 사용자 변경은 보존하고, 불확실한 외부 계약이나 값은 만들지 마.
실제 키는 로컬 환경변수만 사용하고 값이나 인증 URL을 출력하지 마.
작은 변경에는 관련 검사만, 단계 종료에는 정해진 검증을 수행해줘.
검증되지 않은 항목은 통과로 처리하지 마.

원격 DB 변경, Cron 활성화, 배포와 Git 변경은 하지 마.
작업 결과와 검사 결과, 남은 제한을 PROGRESS.md에 기록해줘.
현재 단계의 결과를 보고한 뒤 다음 단계로 자동 진행하지 마.
```

## 12. 작업 종료 보고 형식

매 작업 종료 시 다음 내용을 짧고 사실대로 기록한다.

```text
단계 / 작업 범위:
변경한 핵심 파일:
구현한 사용자 동작:
실행한 검사와 결과:
실행하지 못한 검사와 이유:
외부 설정 또는 승인 대기:
남은 결함과 위험:
다음 단계의 첫 작업:
```

파일 개수나 생성한 코드량을 완료 근거로 삼지 않는다. 사용자 동작, 데이터 정확성, 권한과 실제 검증 결과를 기준으로 판단한다.
