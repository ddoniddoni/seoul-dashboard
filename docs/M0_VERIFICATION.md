# M0 외부 자료 확인 기록

확인일: 2026-10-14, 한국 시간. 최초 공개 자료 조사에 더해 후속 사용자 요청으로 강남역의 실제 API 성공 응답을 1회 확인했다. 운영 활성화 결과는 아니며 다른 장소, 실패 응답과 키 허용량은 미검증이다.

## 공식 장소 카탈로그

출처는 [서울시 실시간 도시데이터 OA-21285](https://data.seoul.go.kr/dataList/OA-21285/F/1/datasetView.do)의 첨부 파일이다. 페이지에 표시된 첨부 수정일은 2026-04-02다. 목록에서 비어 있지 않은 장소 코드 121개를 읽었고 중복 코드는 없었다. 워크시트의 서식 적용 범위 990행을 장소 수로 세지 않았다.

이는 제품 문서의 후보 생활권을 공식 장소에 대응시킨 프로젝트 선택이다. 공식 파일이 이 5개를 추천하거나 비교 가능성을 보장한다는 뜻이 아니다. 원천 명칭은 변경하지 않았다. 관측값, 수집 활성화와 좌표는 이 카탈로그에 넣지 않았다.

머신 판독용 자료는 [initial-area-catalog.json](initial-area-catalog.json)이다. `collectionEnabled=false`이며 웹 지도용 geometry가 아직 없으므로 `geometryAvailable=false`다. 공식 원본 DBF와의 코드 연결 여부는 `sourceGeometryMatched`로 별도 기록했다.

첨부 다운로드는 위 공식 페이지가 제공하는 `downloadFile` 폼을 이용했다. 목적지는 `https://datafile.seoul.go.kr/bigfile/iot/inf/nio_download.do?&useCache=false`이며 POST 필드는 `infId=OA-21285`, `infSeq=2`, 빈 `seqNo`, 아래 `seq`다. 인증키가 필요 없는 공개 파일 다운로드다.

원본 XLSX와 ZIP은 재저장하거나 재압축하지 않고 보존했다. 목록을 읽을 때 openpyxl이 미지원 확장 경고를 냈지만 읽기 전용으로 열었으며 원본 수정은 하지 않았다. 최초 임시 추출 스크립트는 빈 셀에서 행 번호를 읽으려다 중단되었고, 행을 순서대로 열거하도록 수정한 뒤 다시 추출했다.

공식 페이지는 서울특별시를 제공기관과 저작권자로, 공공누리 제1유형 출처표시를 이용허락으로 표시한다. 재가공해 공개할 때 이 출처를 유지한다. 별도 배경지도 타일의 이용조건은 이번 확인 대상이 아니다.

## 영역 파일

- ZIP 내부에는 `.shp`, `.shx`, `.dbf`, `.prj`, `.cpg`, `.qmd`가 있다. GeoJSON이 아니다.
- Shapefile 헤더의 유형은 5(Polygon)이며 DBF에는 121개 레코드와 `AREA_CD`, `CATEGORY`, `AREA_NM` 필드가 있다.
- 초기 5곳의 코드, 명칭, 분류가 목록과 DBF에서 일치한다.
- `.prj`는 `GCS_WGS_1984`, `D_WGS_1984`, degree를 명시한다. `.cpg`는 UTF-8이다. QMD의 CRS 항목은 비어 있으므로 좌표계 근거로 사용하지 않았다.
- 원본 SHP 헤더의 전체 경계는 경도 126.79369~127.164991, 위도 37.415511~37.66202다. 이는 파일 전체의 경계이며 개별 장소 대표점이 아니다.
- 장소별 도형 유효성, 내부 고리, 대표점, 웹 GeoJSON 변환과 화면 일치는 미검증이다. M4에서 확인한다. 이번 단계에서는 좌표나 폴리곤을 새로 만들거나 변환하지 않았다.

## API 계약과 미확인 범위

| 항목 | 이번에 확인한 근거 | 판정 |
| --- | --- | --- |
| 통합 API 형식과 호출 단위 | 데이터셋은 XML, 한 번에 한 장소, 장소명 또는 코드 호출을 안내 | 공개 명세 확인 |
| 인구 전용 API | 매뉴얼 14쪽에서 JSON도 가능하다고 설명 | 통합 XML과 별도 계약으로 취급 |
| 메타 필드 | 강남역 실응답에서 장소 식별과 인구/날씨 핵심 필드 확인 | 성공 응답 1개에 한해 확인 |
| 결과 envelope | root는 `SeoulRtd.citydata`, 실제 성공 태그는 `RESULT/RESULT.CODE`, `RESULT/RESULT.MESSAGE` | 매뉴얼의 `resultCode`/`resultMsg`와 다름. 실패 envelope는 미검증 |
| 성공/실패 코드, 반복 태그와 누락 필드 | 실제 키로 `INFO-000`, 인구/날씨 중첩 wrapper와 예측 배열 확인 | 오류/결측과 다른 장소 변형은 미검증 |
| 원천 기준 시각, 혼잡 단계, 추정 범위, 날씨 값 | 인구 16:40, 날씨 16:50, 붐빔, 78,000~80,000명, 기온 18.4 확인 | 실응답 축약본 보관. 시간대 표기와 단위의 공식 근거는 추가 확인 필요 |
| 전송 | HTTP 8088 정상, HTTPS 8088 TLS 오류, HTTPS 443 8초 timeout | HTTPS 미확인. 이번 로컬 HTTP 1회만 승인, 운영 기본 거부 유지 |
| 키의 실제 호출 허용량 | 인증 성공은 확인했으나 발급 계정의 한도 정보는 확인하지 못함 | 미확인 |
| 응답 크기, 소요시간, 호스팅에서의 접근 | 강남역 182,111 bytes, 로컬 본문 수신까지 약 166ms | 단일 측정. 실제 배포 환경은 미검증 |

[공식 Open API 안내](https://data.seoul.go.kr/together/guide/useGuide.do)의 일일 1,000건 문구는 실시간 지하철 API에 대한 설명이다. 이를 도시데이터 인증키의 보장 한도로 옮기지 않았다. 프로젝트의 `SEOUL_DAILY_CALL_BUDGET=1000`은 설계상 안전 상한일 뿐이다.

후속 요청에서 HTTP의 평문 키 전송 위험을 설명했고, 사용자는 **로컬에서 강남역을 1회 조회하는 범위만** 승인했다. 키를 읽은 서버 프로세스가 공식 host로 요청했고 인증 URL은 출력하지 않았다. 예약, 다른 장소, 공개 운영이나 원격 DB 승인은 포함하지 않는다. HTTPS 443 timeout만으로 HTTPS 미지원을 단정하지 않으며 TLS 검증을 끄지 않았다.

공개 `sample` 키는 강남역 코드 요청에도 기본 장소인 `POI009`를 반환했다. 실제 키의 응답은 `POI014`와 `강남역`이 일치했다. 샘플의 `INFO-000`만으로 장소 조회 성공을 판정하면 안 된다.

인구와 날씨는 각각 `CITYDATA/LIVE_PPLTN_STTS/LIVE_PPLTN_STTS`, `CITYDATA/WEATHER_STTS/WEATHER_STTS` 아래에 있었다. 인구 예측 12개와 날씨 예측 24개는 현재 값과 별도다. 원천 시각 문자열에 offset이 없어 시간대의 공식 근거는 adapter 단계에서 확인한다. 수신 시각은 `2026-10-14T08:10:31.201Z`로 기록했다.

키와 요청 URL 없는 [실응답 축약본](sources/citydata-POI014-20261014.excerpt.xml)과 [메타정보](sources/citydata-POI014-20261014.meta.json)를 보관했다. 축약본은 실제 응답의 인구/날씨 핵심 필드만 추출했으며 예측 배열과 다른 section을 생략했다. 전체 parser 계약 테스트의 fixture를 대체하지 않는다. 상세 경로는 [데이터/API 명세](03_DATA_AND_API.md#실응답에서-확인한-구조)를 따른다.

## 로컬 환경과 다음 확인

최초 M0에는 로컬 키가 없었다. 후속 요청에서는 사용자가 `.env.example`에 키를 입력해 두었지만 Next.js 로더가 그 예시 파일을 자동으로 읽지 않아 `check:env`에 미설정으로 표시됐다. 키를 Git 제외 대상인 `.env.local`로 옮기고 예시의 키는 공란으로 복구했다. 기존 사용자 설정은 보존했고 로컬 비밀 파일 권한을 0600으로 설정했다.

`npm run check:env`는 키와 URL의 **존재 여부만** 출력하며 외부 요청을 수행하지 않는다. 이동 후 서울시 키/URL이 설정됨을 확인했고, DB 설정은 여전히 없다. 수집과 HTTP 운영 허용 기본값은 false다. 파일 조사 중 키가 도구 출력에 포함된 실수가 있어 키 재발급을 권고했다. 노출된 값은 문서에 기록하지 않는다.

실호출은 이번에만 로컬 Node 프로세스로 1회 실행했고, 8초 timeout, redirect 거부, 8 MiB 스트림 제한과 비밀값 없는 오류 출력을 적용했다. XML 조사는 Python 표준 도구로 수행했으며 앱의 XML adapter는 구현하지 않았다. `verify:seoul`을 성공하는 빈 명령으로 추가하지 않았고 전체 parser와 live repository는 M2 이후 범위다. 단위/통합/E2E 테스트는 실행 요청이 없어 계속 보류한다.

## 런타임과 패키지 선택 근거

M2 후속 확인: 공식 API 상세 화면의 출력 필드 설명과 [공식 weather.js](https://data.seoul.go.kr/SeoulRtd/js/domain/weather.js)의 ℃/% 표시로 TEMP/HUMIDITY 단위를 연결했다. PM25는 같은 코드에서 ㎍/㎡와 ㎍/㎥가 혼용되어 연결을 보류했다. 공식 매뉴얼 44쪽을 다시 읽었지만 원천 문자열의 시간대를 확정하는 근거는 찾지 못했다. 따라서 `SEOUL_SOURCE_TIME_ZONE` 또는 CLI 옵션에 명시한 해석 기준을 요구하고 공식 시간대 검증으로 표시하지 않는다. 새 실호출은 없으며 상세 구현/검증 상태는 `PROGRESS.md`의 M2 기록을 따른다.

- [Node.js 릴리스 목록](https://nodejs.org/dist/index.json)에서 24.21.0 LTS(Krypton)와 동봉 npm 11.19.0을 확인했다. 공식 배포 파일을 같은 버전의 `SHASUMS256.txt`와 대조했다.
- [Next.js 설치 문서](https://nextjs.org/docs/app/getting-started/installation)와 공식 npm 메타데이터에서 Next.js 16.4.0, React 19.3.0의 호환 범위를 확인했다. Node.js 최소 요구는 20.9다.
- 최신 TypeScript 7.0.2 대신 `typescript-eslint` 8.71.2의 peer 범위 `<6.1.0`에 맞춰 안정 TypeScript 6.0.3을 선택했다.
- React/JSX/import 린트 플러그인의 peer 범위에 맞춰 ESLint 9.39.5를 선택했다. 설치 시 지원 종료 경고가 있어 향후 호환 플러그인 업데이트 시 해소해야 한다. ESLint 10을 강제 설치하지 않았다.
- [Next.js 환경변수 문서](https://nextjs.org/docs/app/guides/environment-variables)에 따라 서버 설정을 `server-only`로 제한하고, 브라우저 공개 접두사와 `next.config`의 비밀값 주입을 사용하지 않았다.
- [Vitest 공식 안내](https://vitest.dev/guide/)를 참고해 Node 환경의 기본 테스트 설정만 준비했다. 실제 테스트 성공을 확인한 상태는 아니다.
